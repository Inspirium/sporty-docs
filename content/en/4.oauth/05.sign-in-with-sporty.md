If all you need is to know who someone is, you need OpenID Connect, which is
[the authorization code flow](/en/oauth/authorization-code) with `openid` in the scope.

Point any OIDC library at `https://api.sporty.plus/.well-known/openid-configuration` and it
will configure itself. Writing the verification by hand is possible but rarely worth it.

## Get a client id

Anyone with a Sporty account can register an application under
[**Developer**](https://my.sporty.plus/my/developer) in their account menu. You need:

- **a redirect URI**, where Sporty sends people back with a code;
- optionally, **a sign-out redirect URI**, where Sporty may send people after they
  [sign out](#signing-out);
- whether your app **has a server that can keep a secret**. Turn this off for an app that
  runs only in the browser or on a phone. It then gets no secret and signs in with PKCE alone.

A new application works **only for you** until Sporty has reviewed it. Build and test it
end to end, then [contact us](mailto:info@sporty.plus) to have it reviewed. Until then,
anyone else who tries it sees a warning, and the sign-in does not go through.

An application built for one club can also be registered by that club's administrator, under
**Settings → API clients**. See [Registering an application](/en/oauth/clients).

## The id_token

Returned alongside the access token when `openid` was granted. An RS256 JWT:

```json
{
  "iss": "https://api.sporty.plus",
  "sub": "9f1c2e40-...",
  "aud": "your-client-id",
  "iat": 1789304059,
  "nbf": 1789304059,
  "exp": 1789307659,
  "auth_time": 1789301200,
  "amr": ["pwd", "otp", "mfa"],
  "nonce": "what-you-sent",
  "at_hash": "xQ7f...",
  "name": "Ada Lovelace",
  "given_name": "Ada",
  "family_name": "Lovelace",
  "locale": "hr",
  "picture": "https://...",
  "email": "ada@example.com",
  "email_verified": true
}
```

| Claim | Notes |
| --- | --- |
| `sub` | The member's permanent id. **This is the one to store.** It never changes; an email address can. |
| `aud` | Your client id. Check it. |
| `nonce` | Present if you sent one. Check it. |
| `at_hash` | Binds this id_token to the access token issued with it. |
| `auth_time` | When the member signed in to Sporty. For a few sessions that are older than this feature, it is the moment they approved your app instead. |
| `amr` | How they signed in. See [below](#how-the-member-signed-in). Absent for those same older sessions. |
| `name`, `given_name`, `family_name`, `locale`, `picture` | With `profile`. |
| `email`, `email_verified` | With `email`. |
| `phone_number`, `phone_number_verified` | With `phone`, when the member has a number. `phone_number_verified` is always `false`: Sporty does not verify phone numbers. |
| `clubs` | With `clubs`. See [below](#the-clubs-claim). |

### How the member signed in

`amr` uses the values of [RFC 8176](https://www.rfc-editor.org/rfc/rfc8176):

| `amr` | Sign-in |
| --- | --- |
| `["pwd"]` | Password |
| `["pwd", "otp", "mfa"]` | Password and an authenticator app code |
| `["pwd", "mfa"]` | Password and a recovery code |
| `["hwk", "mfa"]` | A passkey |
| `["fed"]` | Google, Apple, Microsoft, DUPR or the member's organisation |
| `["fed", "mfa"]` | The member's organisation, which reported multi-factor sign-in |

If your application needs a second factor, check that `amr` contains `mfa`. If it does not,
tell the member to turn on two-factor sign-in in Sporty.

### The `clubs` claim

With the `clubs` scope you get the clubs the member belongs to. That means a club where they
hold a membership that has not ended, or have a staff role. This is enough to answer "is this
person a member of club X" without the [partner API](/en/oauth/partner-api).

```json
"clubs": [
  {
    "id": 42,
    "name": "TK Jarun",
    "url": "https://tkjarun.hr",
    "membership": { "name": "Annual", "end": "2027-03-31T23:59:59+00:00" },
    "roles": []
  },
  {
    "id": 77,
    "name": "Padel Centar",
    "url": null,
    "membership": null,
    "roles": ["cashier"]
  }
]
```

`membership.end` is `null` for a membership with no end date. `roles` is any of `admin`,
`cashier` and `employee`.

## Prompt and max_age

Both go on the [authorize request](/en/oauth/authorization-code#_2-send-the-member-to-sporty).

| You send | What happens |
| --- | --- |
| `prompt=none` | Nothing is shown. If the member is signed in to Sporty and has already approved everything you ask for, you get a code straight away. Otherwise you get `error=login_required`, `consent_required` or `interaction_required` at your redirect URI. Use it to check silently whether someone is still signed in. |
| `prompt=login` | The member signs in to Sporty again before approving, even if they already are. |
| `max_age=600` | The same, but only if their Sporty session is more than 600 seconds old. Then check `auth_time`. |
| `prompt=consent` | The consent screen is shown. Sporty always shows it outside `prompt=none`, so this changes nothing. |
| `login_hint=ada@example.com` | Pre-fills the email address on the sign-in page. |

`prompt=none` cannot be combined with other values.

## Signing out

When someone signs out of your application, send them to the `end_session_endpoint`:

```
https://api.sporty.plus/oauth2/logout
  ?id_token_hint=THE_ID_TOKEN
  &post_logout_redirect_uri=https://yourapp.example/signed-out
  &state=RANDOM
```

| Parameter | Notes |
| --- | --- |
| `id_token_hint` | The id_token you were given. An expired one is fine. |
| `client_id` | Instead of the hint, if you no longer have it. |
| `post_logout_redirect_uri` | Optional. It must be one of the sign-out redirect URIs you registered. |
| `state` | Optional. It comes back on the redirect. |

Sporty asks the member whether to sign out of Sporty too, then sends them to your
`post_logout_redirect_uri`. Sporty does not revoke your tokens:
[revoke](/en/oauth/authorization-code#_7-revoke-when-you-are-done) them yourself if your
application should forget the member.

## Verifying it

Fetch `https://api.sporty.plus/oauth2/jwks`, pick the key whose `kid` matches the token
header, verify RS256, then check `iss`, `aud` and `exp`.

```bash
curl https://api.sporty.plus/oauth2/jwks
```

Cache the JWKS — an hour is sensible — but re-fetch when you meet a `kid` you do not know,
rather than failing.

## /userinfo

An id_token is a snapshot. For current values:

```bash
curl https://api.sporty.plus/oauth2/userinfo \
  -H "Authorization: Bearer $ACCESS_TOKEN"
```

The same claims, gated the same way by scope, always including `sub`.

Use the [Sign in with Sporty button](/en/oauth/sign-in-button), so people recognise it.

## Key rotation

We rotate the signing key rarely, and when we do:

- the new public key appears in the JWKS, alongside the old one, before anything is signed
  with it;
- **every existing access token stops working.** The signing key is shared with access
  tokens, so a rotation ends them. Your refresh tokens survive — use them, and be ready to
  re-authorise if that fails.

If you ever see a valid-looking token suddenly rejected, refresh once before assuming
anything is broken.
