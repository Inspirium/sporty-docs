Si vous avez seulement besoin de savoir qui est une personne, il vous faut OpenID Connect,
c'est-à-dire [le flux du code d'autorisation](/fr/oauth/authorization-code) avec `openid` dans
le scope.

Faites pointer n'importe quelle bibliothèque OIDC vers
`https://api.sporty.plus/.well-known/openid-configuration` et elle se configurera toute seule.
Écrire la vérification à la main est possible, mais en vaut rarement la peine.

## Obtenir un client id

Toute personne ayant un compte Sporty peut enregistrer une application sous
[**Développeur**](https://my.sporty.plus/my/developer), dans le menu de son compte. Il vous faut :

- **une URI de redirection**, où Sporty renvoie les gens avec un code ;
- éventuellement **une URI de redirection après déconnexion**, où Sporty peut renvoyer les gens
  après leur déconnexion (voir *Se déconnecter* plus bas) ;
- savoir si votre application **dispose d'un serveur capable de garder un secret**. Désactivez
  cette option pour une application qui fonctionne uniquement dans le navigateur ou sur un
  téléphone. Elle ne reçoit alors pas de secret et se connecte avec PKCE seul.

Une nouvelle application ne fonctionne **que pour vous** tant que Sporty ne l'a pas examinée.
Construisez-la et testez-la de bout en bout, puis [contactez-nous](mailto:info@sporty.plus)
pour la faire examiner. D'ici là, toute autre personne qui l'essaie voit un avertissement, et la
connexion n'aboutit pas.

Une application créée pour un seul club peut aussi être enregistrée par l'administrateur de ce
club, sous **Paramètres → Clients API**. Voir [Enregistrer une application](/fr/oauth/clients).

## L'id_token

Renvoyé avec le jeton d'accès lorsque `openid` a été accordé. Un JWT RS256 :

```json
{
  "iss": "https://api.sporty.plus",
  "sub": "9f1c2e40-...",
  "aud": "your-client-id",
  "iat": 1789304059,
  "nbf": 1789304059,
  "exp": 1789307659,
  "auth_time": 1789301200,
  "amr": ["pwd", "otp", "mfa"],
  "nonce": "what-you-sent",
  "at_hash": "xQ7f...",
  "name": "Ada Lovelace",
  "given_name": "Ada",
  "family_name": "Lovelace",
  "locale": "hr",
  "picture": "https://...",
  "email": "ada@example.com",
  "email_verified": true
}
```

| Claim | Remarques |
| --- | --- |
| `sub` | L'identifiant permanent du membre. **C'est celui-ci qu'il faut stocker.** Il ne change jamais ; une adresse e-mail, si. |
| `aud` | Votre client id. Vérifiez-le. |
| `nonce` | Présent si vous en avez envoyé un. Vérifiez-le. |
| `at_hash` | Lie cet id_token au jeton d'accès émis avec lui. |
| `auth_time` | Le moment où le membre s'est connecté à Sporty. Pour quelques sessions plus anciennes que cette fonctionnalité, c'est le moment où il a approuvé votre application. |
| `amr` | Comment il s'est connecté, voir plus bas. Absent pour ces mêmes sessions plus anciennes. |
| `name`, `given_name`, `family_name`, `locale`, `picture` | Avec `profile`. |
| `email`, `email_verified` | Avec `email`. |
| `phone_number`, `phone_number_verified` | Avec `phone`, quand le membre a un numéro. `phone_number_verified` vaut toujours `false` : Sporty ne vérifie pas les numéros de téléphone. |
| `clubs` | Avec `clubs`, voir plus bas. |

### Comment le membre s'est connecté

`amr` utilise les valeurs de la [RFC 8176](https://www.rfc-editor.org/rfc/rfc8176) :

| `amr` | Connexion |
| --- | --- |
| `["pwd"]` | Mot de passe |
| `["pwd", "otp", "mfa"]` | Mot de passe et code d'une application d'authentification |
| `["pwd", "mfa"]` | Mot de passe et code de récupération |
| `["hwk", "mfa"]` | Une clé d'accès (passkey) |
| `["fed"]` | Google, Apple, Microsoft, DUPR ou l'organisation du membre |
| `["fed", "mfa"]` | L'organisation du membre, qui a signalé une connexion multifacteur |

Si votre application exige un second facteur, vérifiez que `amr` contient `mfa`. Sinon,
demandez au membre d'activer la connexion à deux facteurs dans Sporty.

### Le claim `clubs`

Avec le scope `clubs`, vous obtenez les clubs auxquels le membre appartient : ceux où il a un
abonnement qui n'est pas terminé, ou un rôle dans le personnel. Cela suffit pour répondre à
« cette personne est-elle membre du club X » sans l'[API partenaire](/fr/oauth/partner-api).

```json
"clubs": [
  {
    "id": 42,
    "name": "TK Jarun",
    "url": "https://tkjarun.hr",
    "membership": { "name": "Annuel", "end": "2027-03-31T23:59:59+00:00" },
    "roles": []
  },
  {
    "id": 77,
    "name": "Padel Centar",
    "url": null,
    "membership": null,
    "roles": ["cashier"]
  }
]
```

`membership.end` vaut `null` pour un abonnement sans date de fin. `roles` peut contenir
`admin`, `cashier` et `employee`.

## Prompt et max_age

Les deux se placent dans la [demande d'autorisation](/fr/oauth/authorization-code).

| Vous envoyez | Ce qui se passe |
| --- | --- |
| `prompt=none` | Rien n'est affiché. Si le membre est connecté à Sporty et a déjà approuvé tout ce que vous demandez, vous recevez un code immédiatement. Sinon, vous recevez `error=login_required`, `consent_required` ou `interaction_required` sur votre URI de redirection. Utilisez-le pour vérifier en silence si quelqu'un est toujours connecté. |
| `prompt=login` | Le membre se reconnecte à Sporty avant d'approuver, même s'il l'est déjà. |
| `max_age=600` | La même chose, mais seulement si sa session Sporty date de plus de 600 secondes. Vérifiez ensuite `auth_time`. |
| `prompt=consent` | L'écran de consentement s'affiche. Sporty l'affiche toujours en dehors de `prompt=none`, cela ne change donc rien. |
| `login_hint=ada@example.com` | Pré-remplit l'adresse e-mail sur la page de connexion. |

`prompt=none` ne peut pas être combiné avec d'autres valeurs.

## Se déconnecter

Quand quelqu'un se déconnecte de votre application, envoyez-le vers l'`end_session_endpoint` :

```
https://api.sporty.plus/oauth2/logout
  ?id_token_hint=THE_ID_TOKEN
  &post_logout_redirect_uri=https://yourapp.example/signed-out
  &state=RANDOM
```

| Paramètre | Remarques |
| --- | --- |
| `id_token_hint` | L'id_token que vous avez reçu. Un id_token expiré convient. |
| `client_id` | À la place du hint, si vous ne l'avez plus. |
| `post_logout_redirect_uri` | Facultatif. Doit être l'une des URI de redirection après déconnexion que vous avez enregistrées. |
| `state` | Facultatif. Il revient avec la redirection. |

Sporty demande au membre s'il veut aussi se déconnecter de Sporty, puis l'envoie vers votre
`post_logout_redirect_uri`. Sporty ne révoque pas vos jetons :
[révoquez-les](/fr/oauth/authorization-code) vous-même si votre application doit oublier le
membre.

## Le vérifier

Récupérez `https://api.sporty.plus/oauth2/jwks`, choisissez la clé dont le `kid` correspond à
l'en-tête du jeton, vérifiez la signature RS256, puis contrôlez `iss`, `aud` et `exp`.

```bash
curl https://api.sporty.plus/oauth2/jwks
```

Mettez le JWKS en cache — une heure est raisonnable — mais récupérez-le à nouveau lorsque vous
rencontrez un `kid` inconnu, plutôt que d'échouer.

## /userinfo

Un id_token est un instantané. Pour les valeurs actuelles :

```bash
curl https://api.sporty.plus/oauth2/userinfo \
  -H "Authorization: Bearer $ACCESS_TOKEN"
```

Les mêmes claims, filtrés de la même façon selon le scope, avec toujours `sub`.

## Le bouton

Utilisez le [bouton Se connecter avec Sporty](/fr/oauth/sign-in-button), pour que les gens le
reconnaissent.

## Rotation des clés

Nous renouvelons rarement la clé de signature, et quand nous le faisons :

- la nouvelle clé publique apparaît dans le JWKS, à côté de l'ancienne, avant que quoi que ce
  soit ne soit signé avec elle ;
- **tous les jetons d'accès existants cessent de fonctionner.** La clé de signature est
  partagée avec les jetons d'accès, donc une rotation y met fin. Vos jetons de rafraîchissement
  survivent — utilisez-les, et soyez prêt à redemander l'autorisation si cela échoue.

Si un jeton d'apparence valide est soudain rejeté, rafraîchissez-le une fois avant de supposer
que quelque chose est cassé.
